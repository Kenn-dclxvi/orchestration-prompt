# エージェントオーケストレーションプロセス

## 目的
この文書は、任意のリポジトリに適用できる AI 駆動開発プロセスの運用仕様を定義する。

対象は、指示書作成、親エージェント運用、証明道具箱、独立実行枠、実装SA、監査SA、レビューSAの関係である。

この文書はアプリケーション仕様ではなく、開発環境における AI エージェント運用プロセスの仕様である。

## 位置づけ
この文書は `docs/` 配下に置く。

現行運用ルールの正本は本文書に一本化する。`docs/orchestration-v2.md` は設計履歴/rationale であり、現行運用ルールではない。矛盾がある場合は本文書を優先する。

本文書は、要求から実装完了までを Execution Lifecycle として運用構造化し、v1 で確立した責務分離、情報分離、停止条件、完了判定の意味を保存する。語彙は v2 設計に由来するが、実装、監査、レビュー、停止、完了判定の運用ルールは本文書が正本である。

関連文書:

## Execution Lifecycle
このプロセスの実行ライフサイクルは、Requirement → Goal Definition → Planning → Dependency Planning → Task Graph → Parallel Scheduling → Execution → Continuous Verification → Replan → Goal Complete である。

このライフサイクルは、Goal → Planning → Execution → Verification → Replan → Goal Complete の流れを中心に構成する。各段階は、本文書の運用ルール（作業単位化、実装、監査、レビュー、停止、完了判定）を語彙として整理するものであり、責務分離と情報分離を弱めない。

各段階の責務は次のとおりである。

- Requirement: 要求を受け取り、明示された対象、範囲、制約、完了条件を識別する。
- Goal Definition: 要求を達成すべきゴールとして定義し、成功条件を明確にする。
- Planning: ゴール達成に必要なタスク、依存関係、優先順位、実行順序を設計する。
- Dependency Planning: 各タスクの前提条件、依存先、計画上の並列可能性を解析する。
- Task Graph: タスクを有向グラフとして表現する。
- Parallel Scheduling: 依存関係のないタスクを計画上並列可能な作業として識別し、待ち時間を減らす実行順序候補を作る。物理並列の実行許可ではない。
- Execution: 承認済み範囲に従って実装、修正、確認を行う。
- Continuous Verification: 各段階で品質条件、制約、成果物、テスト結果を確認する。
- Replan: 実行と検証で得た観測事実を親エージェントへ返し、作業単位化し直すか Plan へ戻すかの判断材料にする。
- Goal Complete: 要求を満たし、品質基準を満たした状態を完了として扱う。

## Planning Engine
Planning Engine は、このプロセスの中心概念である。実装開始前に最適な実行計画を構築し、実行中も観測事実に応じて計画を更新するための機構である。

Planning Engine が扱う計画観点は、Goal Definition、Dependency Planning、Task Graph、Parallel Scheduling、実行順序の決定、Replan条件整理、Quality Gate観点整理、構成判断後の詳細計画見積もりである。これらは計画上の整理観点であり、実行許可、Scope、Done、テスト条件、SA起動権限を生成しない。

Planning Engine は、単純な ToDo を作るだけではない。ゴール達成までの探索空間を整理し、品質を落とさずに最終的な完了時間を短くする経路を選択する。ただし境界が不足している場合、境界を補完せず不足項目を返す。計画整理ツールを載せた独立実行枠が扱う計画観点と禁止事項は §Parent→Plan の受け渡し契約 に従う。

## Optimization Principle
Optimization Principle は、Planning Engine が計画を最適化するときの優先順位である。

優先順位は次の順序とする。

1. Goal 達成
2. 品質維持
3. 実装時間短縮
4. 手戻り最小化
5. コンテキスト切替最小化

目先の作業時間が短い経路を選ばない。品質低下、手戻り、再確認、依存待ちを含めた最終的な完了時間が最小となる経路を選択する。この優先順位は、情報分離、レビュー必須ゲート、停止条件を弱める根拠にしない。品質維持と情報分離は実装時間短縮に優先する。

## 証明道具箱方式
証明道具箱方式は、固定された Plan / Audit / Review の起動順を出発点にせず、希望成果物の安全証明に必要な証明ツールを選び、必要に応じて独立実行枠へ分離する構成判断である。安全とは、希望した成果物が出ていることを、適切な証拠と適切なコストで説明できる状態である。安全性を削って高速化してはならず、安全証明に不要な過剰コストだけを減らす。

証明道具箱は、希望成果物の安全証明に使う証明ツールの一覧である。証明道具箱は独立実行枠ではなく、工程でもなく、親エージェントが直接実行する道具でもない。

証明ツールは、証明に使う観点、制約、入力契約、出力契約、禁止事項、確認項目、証拠要求のまとまりである。証明ツールには、計画整理ツール、実装ツール、契約照合ツール、品質確認ツール、安全確認ツール、敵対的確認ツール、証拠収集ツール、出荷確認ツールを含めてよい。証明ツールを選ぶことは観点・制約・証明能力を増やすことであり、独立実行枠を増やすことではない。

独立実行枠は、選ばれた証明ツールを1つ以上読み込んで動く分離コンテキストである。従来のSAに相当するが、固定工程名や固定人格として扱わない。独立実行枠への分離は、並列稼働・情報制御・バイアス制御のいずれかに意味がある場合にだけ行う。

構成判断は、どの証明ツールを使うか、どの証明ツールを同じ独立実行枠へ載せるか、どの証明ツールを別の独立実行枠へ分離するかを決める判断である。親エージェントの初動は、固定SAを選ぶことではなく、この構成判断から始める。誤った動線は「Plan SA を使うか / Audit SA を使うか / Review SA を使うか」である。正しい動線は「希望成果物の安全証明に必要な証明ツールは何か / それらを同じ独立実行枠にまとめてよいか / 分離する必要があるなら、その理由は何か」である。

最小証明セットは、希望成果物を説明するために最初に選ぶ最小限の証明ツール群である。親は最小証明セットから始め、Risk / Ambiguity / Impact / Proof Gap を見て必要な証明ツールだけを追加する。軽量化は、必要な証明を削ることではなく、過剰な証明ツール、過剰な入力、過剰な独立実行枠、過剰な文脈複製を避けることである。

証明ツールの追加条件は次のとおりである。

- 計画整理ツール: Scope / Done / Tests が実行前に整理できない、複数工程や依存関係がある、実行順序で手戻りが起きそう、Replan条件を先に整理する必要がある。
- 実装ツール: 承認済み実装指示書または明示された作業単位化条件に基づき、必要に応じて実行契約と矛盾しない範囲で、対象・範囲・完了条件・テスト条件・停止条件が推定なしで確定しており、実装または修正を行う必要がある。
- 契約照合ツール: 成果物が契約と一致していることを確認する必要がある、テストだけでは契約準拠の証明が弱い、仕様境界が重要、実装側の自己判断混入を検出したい。
- 品質確認ツール: 設計品質を見る必要がある、周辺影響を見る必要がある、テスト妥当性を見る必要がある、将来保守性や運用影響を見る必要がある。
- 安全確認ツール: 本番運用に影響する、データ永続化に影響する、権限・認証・外部送信・破壊的操作に触れる、失敗時の影響が大きい。
- 敵対的確認ツール: 成功前提ではなく失敗仮説で確認する必要がある、実装者の自己正当化を排除したい、レビュー観点を意図的に厳しくしたい、仕様の抜け・矛盾・過剰解釈を攻撃的に探す必要がある。
- 証拠収集ツール: 完了証拠が散らばっている、テスト・差分・ログ・実行結果をまとめる必要がある、後続の監査やレビューに渡す証拠を整理する必要がある。
- 出荷確認ツール: 完了報告またはPR作成の前に、必要な証拠、契約照合、品質確認、レビュー必須ゲート、除外操作の遵守を最終確認する必要がある。

独立実行枠へ分離する条件は、次の3基準に限定する。

- 並列稼働: 依存関係が独立している、分けた方が待ち時間や手戻りが減る、片方の結果を待たずに進められる。単に速そう、便利そうという理由では分離しない。
- 情報制御: 見せる情報を変えないと役割の意味が崩れる、実装経緯を見せると契約照合が甘くなる、監査結果を見せるとレビューが引っ張られる、敵対的確認に実装者の意図説明を見せると独立性が落ちる。情報遮断に意味がある場合だけ分離する。
- バイアス制御: 同じ文脈で見ると判断が歪む、実装者の自己正当化を避けたい、成功前提の確認を避けたい、契約準拠と品質判断を混ぜたくない、敵対的確認を独立させたい。同じ独立実行枠に載せると確認品質が落ちる場合だけ分離する。

親エージェントは構成判断の判断ログを必ず残す。判断ログがない省略は軽量化ではなく手抜きとして扱う。判断ログは最低限、希望成果物、最小証明セット、必要な証明ツール、選択した証明ツール、選択しなかった証明ツール、同じ独立実行枠にまとめた証明ツール、別の独立実行枠へ分離した証明ツール、分離理由、並列稼働の価値、情報制御の必要性、バイアス制御の必要性、Risk / Ambiguity / Impact / Proof Gap、過剰コストとして採用しなかった証明ツール、実行契約へ渡す内容を含む。

実行契約は、実行側に渡す最終権威である。構成判断は実行権威を生成せず、Scope / Done / Test / Permission を補完しない。実行契約は最低限、`target_files`、`scope`、`done_condition`、`forbidden_operations`、`execution_instructions`、`selected_tools`、`execution_frames`、`required_evidence`、`required_checks`、`verification_commands`、`block_conditions`、`output_contract` を含む。実行側は、承認済みの実行契約、承認済み実装指示書、`target / scope / done / tests / stop` が矛盾しない範囲だけを実行入力として扱う。

本方式を反映する変更対象は `AGENTS.md`、`docs/orchestration-process.md`、`prompts/plan.md`、`docs/orchestration-v2.md`、`AI_CHAT_BUNDLE.txt` である。範囲は、証明道具箱方式の構成判断、証明ツール選択、独立実行枠分離、判断ログ、軽量化、実行契約との関係を現行運用へ接続することに限る。非対象は、既存SAの全面廃止、実装・監査・レビュー手順の全面変更、レビュー必須ゲートの無条件緩和、親の直接実装許可、DSL意味変更、`commit` / `push` / `deploy` / 外部送信の許可変更、`docs/orchestration-v2.md` を現行ルールへ戻すことである。主なリスクは、固定SA起点へ戻ること、Plan SA ありきの動線になること、軽量化を理由に情報制御またはバイアス制御を弱めること、構成判断から実行許可を生成してしまうことである。

## 基本方針
AI 駆動開発プロセスは、以下の責務分離を前提にする。

```text
指示書作成
  ユーザー依頼を整理し、実装指示書を作成する。

親エージェント
  承認済み実装指示書を理解し、実行状況を管理する。

実装SA
  実装を行う。

監査SA
  非破壊で契約準拠の判定を行う。

レビューSA
  PRレビュー相当の品質確認を非破壊で行う。
```

親エージェントは、承認済み実装指示書または明示された作業単位化条件がある場合に限り、実装SAを起動する。依頼を `target / scope / done / tests / stop` に分解できない場合、または分解に AI側の補完が必要な場合は停止する。

ユーザーは、草案が明示条件を満たすなら追加確認なしで作業単位化して実行してよい、という条件付き事前承認を先に宣言できる。条件付き事前承認の成立要件・ID照合・除外操作は §条件付き事前承認テンプレート に従う。

条件付き事前承認テンプレートと既定テスト定義は、明示済み条件をIDで参照するための定義である。IDは境界を生成せず、未定義の対象・範囲・完了条件・品質基準・実行許可・テスト条件を補完しない。

親エージェントは、実装・修正・テスト実行・監査・監査後の PRレビュー相当の品質確認を直接行わない。指示書作成も直接行わず、ユーザーが指示書作成を明示依頼した場合、または実装・変更の意図がありながら作業単位化に必要な対象・範囲・完了条件・品質基準・実行許可を推定なしで確定できない場合に、計画整理ツールを載せた独立実行枠としてプランSAを起動する。

プランSAを起動する場合、親エージェントは §Parent→Plan の受け渡し契約に従い、明示入力、正本参照、構成判断ログを分離して渡す。

## 条件付き事前承認テンプレート
条件付き事前承認テンプレートは、ユーザー入力、承認済み実装指示書、または明示された参照文書で定義された場合だけ使う。

テンプレートは以下を含む。

- `template_id`
- 条件
- 対象
- 範囲
- 完了条件
- 品質基準
- 実行許可
- 除外操作

条件・対象・範囲・完了条件・品質基準・実行許可・除外操作は、値そのもの、閉じた列挙、または推定なしで照合できる条件として明示されている必要がある。

条件付き事前承認は、条件・対象・範囲・完了条件・品質基準・実行許可が明示され、条件充足を推定で判断せず確認できる場合だけ作業単位化条件として扱う。AI は条件・対象・範囲・完了条件・品質基準・実行許可を補完してはならない。条件充足を推定で判断する必要がある場合は停止する。

親エージェントは、テンプレートIDとユーザー入力または草案の該当内容を照合する。照合結果が一意であり、かつ全項目が満たされる場合だけ、作業単位化条件として扱う。複数候補、未定義項目、曖昧条件、条件充足に推定が必要な項目がある場合は停止する。

草案にテンプレートIDが含まれていても、草案自体は実行許可ではない。テンプレートIDは、親エージェントが条件付き事前承認との照合に使う情報であり、承認・実装許可を生成しない。

`commit` / `push` / `deploy` / 外部送信は、テンプレートの除外操作に含める。これらは別途明示許可がある場合だけ実行許可として扱う。

## 既定テスト定義
既定テスト定義は、ユーザー入力、承認済み実装指示書、または明示された参照文書で定義された場合だけ使う。

既定テスト定義は以下を含む。

- `default_test_id`
- 適用条件
- テスト条件
- `なし（根拠）` を許可する条件

テスト条件は、実行するテストコマンド、または `なし（根拠）` として明示する。コード変更を含む作業単位ではテストコマンド必須とし、`なし（根拠）` を使ってはならない。

親エージェントは、既定テストIDと適用条件を推定なしで照合する。照合結果が一意であり、かつ適用条件が満たされる場合だけ、テスト条件を展開して `tests` に入れる。既定テストIDだけがあり、展開済みのテストコマンドまたは `なし（根拠）` を確定できない場合は停止する。

実装SAへ渡す `tests` は、既定テスト定義から展開済みのテストコマンドまたは `なし（根拠）` とする。実装SAは既定テストを選ばない。

## 作業単位化判定フロー
親エージェントは、以下の順序で作業単位化を判断する。

1. 承認済み実装指示書または作業単位化対象のユーザー入力を確認する。
2. 条件付き事前承認テンプレートを使う場合は、テンプレートID、条件、対象、範囲、完了条件、品質基準、実行許可、除外操作を §条件付き事前承認テンプレート に従って照合する。
3. 草案または Plan 成果物を入力に含める場合は、それ自体が実行許可ではないことを維持し、条件付き事前承認または別途明示許可との照合対象としてだけ扱う。Plan 成果物を実装SAへ渡す場合は、§Plan→Execution の受け渡し契約に従う。
4. `target / scope / done` を明示項目だけで整理できるか確認する。
5. 明示テスト条件または既定テスト定義を確認し、既定テスト定義を使う場合は §既定テスト定義 に従って既定テストIDと適用条件を照合して `tests` に展開する。
6. コード変更を含む作業単位で `tests` がテストコマンドにならない場合は停止する。テストコマンド必須・`なし（根拠）` 可否は §既定テスト定義 に従う。
7. `target / scope / done / tests / stop` のいずれかに AI側の補完が必要な場合は停止する。
8. すべてを推定なしで整理できる場合だけ、実装SAへ渡す。

作業単位化可否は `可否 / 理由 / 草案または不足項目` の形式で返す。

## Parent→Plan の受け渡し契約
親エージェントがプランSAを起動する場合、親エージェントは Parent→Plan Contract として、親が保持している明示入力と正本参照だけを渡す。Parent→Plan Contract は実行許可を生成せず、未定義の境界項目を補完しない。

Parent→Plan Contract は、最低限以下を含む。

- ユーザー要求: ユーザーが明示した依頼本文、意図、質問、制約。
- 明示された対象: ユーザー入力、承認済み実装指示書、または明示された参照文書で示された対象。
- 明示された範囲: 変更可能範囲、参照可能範囲、非対象、除外操作。
- 制約: 禁止操作、停止条件、品質基準、参照条件、適用先固有の制約。
- 実行許可の有無: 実装・変更・テスト・外部送信などの許可が明示されているか。
- 既定テスト定義: 明示された定義、ID、適用条件、展開前のテスト条件。
- 条件付き事前承認: 明示されたテンプレート、条件、境界項目、除外操作。
- SSOT: 正本として扱う文書、優先順位、参照してよい範囲。
- 構成判断ログ: 親が独立実行枠の起動前に行った、希望成果物、最小証明セット、証明ツールの選択・非選択、同一枠にまとめた理由、分離理由、Risk / Ambiguity / Impact / Proof Gap、未指定項目。

プランSAが扱ってよい計画観点は以下に限る。これらは Plan 段階の整理観点であり、実装、監査、レビュー、停止、完了判定の運用ルールを変更しない。

- Goal Definition: 明示された目的、対象、範囲、完了条件、品質基準の整理。
- Dependency Planning: 作業間の前提条件、依存先、独立性の整理。
- Task Graph 草案: 明示境界内の作業要素と依存関係の草案化。
- Parallel Scheduling 草案: 物理並列ではなく、計画上の独立性と順序候補の整理。
- Replan条件整理: 後続工程で Plan へ戻すべき観測事実の整理。
- Quality Gate観点整理: 草案が明示境界、正本、テスト条件と矛盾しないかの観点整理。
- Detailed Planning / Detailed Estimate: 作業規模、分離価値、リスク、トークン効率、再修正確率、後続証明ツール構成案を、計画整理ツール起動後の詳細判断材料として整理する。

プランSAは以下をしてはならない。

- 実行許可の生成。
- Scope補完。
- Done補完。
- テスト条件の推定。
- Contract外の対象追加。
- 実装。
- 監査。
- レビュー。

## 構成判断 / Orchestration Cost Gate 要件
この要件は、親エージェントの初動で行う構成判断と、必要に応じて独立実行枠へ渡す詳細整理を分離するための要件である。作業規模だけでSA起動を決めず、希望成果物、最小証明セット、分離価値、リスク、トークン効率、再修正確率を合わせて扱う。

責務分離は次の2段階とする。

```text
Parent
  └─ 構成判断 / 判断ログ

独立実行枠
  └─ 選択された証明ツールによる詳細整理または確認
```

この要件は実行許可、Scope、Done、テスト条件、SA起動権限を生成しない。実装、監査、レビュー、停止、完了判定の運用ルールを置き換えず、親の直接実装を許す抜け道にしない。

全体構造は次のとおりである。

```text
Parent
  ↓
構成判断 / 判断ログ
  ↓
必要なら計画整理ツールを載せた独立実行枠
  ↓
Execution Contract
  ↓
実装ツールを載せた独立実行枠
  ↓
契約照合ツールを載せた独立実行枠
  ↓
品質確認ツールを載せた独立実行枠
```

親は、独立実行枠の起動前に構成判断として、希望成果物の安全証明に必要な証明ツールと分離理由だけを扱う。親が見るものは次に限る。

- ユーザー要求の明確さ。
- 変更対象の明示有無。
- 修正規模の概算。
- リスク。
- 希望成果物。
- 最小証明セット。
- Risk / Ambiguity / Impact / Proof Gap。
- 証明ツールを追加する価値。
- 独立実行枠へ分離する価値。
- 並列稼働、情報制御、バイアス制御の必要性。
- 独立実行枠が過剰かどうか。

親は構成判断で次をしてはならない。

- 実装計画の詳細化。
- Task Graph の具体化。
- Done の補完。
- Scope の補完。
- テスト条件の推定。
- 実装判断。

親の構成判断の判定対象は次に限る。

- 希望成果物の安全証明に必要な証明ツールは何か。
- どの証明ツールを同じ独立実行枠へまとめてよいか。
- どの証明ツールを別の独立実行枠へ分離する必要があるか。
- 採用しない証明ツールが過剰コストとして説明できるか。

軽量化の判定は、§証明道具箱方式、§SA利用ケース、§作業単位化判定フロー、§レビューSA入力、§親エージェントの制約内でだけ扱う。軽量化は、親の直接実装、監査省略、レビュー必須ゲートの省略、情報分離の緩和、バイアス制御の省略を意味しない。

軽量化と分離の選択は、作業規模だけで決めない。作業規模、情報制御価値、バイアス制御価値、Risky 有無を併せて判断する。構成は固定割り当てではなく、Orchestration Cost Gate は並列稼働・情報制御・バイアス制御の評価後に扱う。軽量化する場合でも、監査SAへ実装経緯・事前評価を渡さず、レビューSAへ監査結果本文・監査SAの指摘内容を渡さず、Audit Contract / レビューSA入力の情報遮断を維持する。

計画整理ツールを載せた独立実行枠は、起動後に Detailed Planning / Detailed Estimate として、より詳細な計画見積もりを行う。計画整理ツールが見るものは次に限る。

- Goal Definition。
- Dependency Planning。
- Task Graph 草案。
- Parallel Scheduling 草案。
- Replan条件。
- Quality Gate観点。
- 後続証明ツール構成案。
- テスト要求の整理。

計画整理ツールは後続の証明ツール構成案や詳細判断材料を出してよい。ただし計画整理ツールも親の構成判断を置き換えず、実行許可、Scope、Done、テスト条件、SA起動権限を生成しない。

構成判断は次の順序で判断する。Detailed Planning / Detailed Estimate は、親の構成判断ログを入力として同じ観点の詳細判断材料を整理するだけであり、親の最小証明セット選択や分離判断を置き換えない。

1. 最小証明セット: 親が、希望成果物を説明するために必要な最小限の証明ツールを選ぶ。計画整理ツールは選択済みセットの根拠と詳細判断材料を整理する。
2. 分離判断: 親が、並列稼働、情報制御、バイアス制御の価値を評価する。計画整理ツールは親の評価結果を詳細化する。
3. Orchestration Cost Gate: 親が、分離判断の結果を維持したうえで、トークン効率と独立実行枠数を評価する。計画整理ツールは評価材料を整理する。

Orchestration Cost Gate は分離判断の後にだけ評価する。情報制御またはバイアス制御の価値が高い確認は、効率が悪くても分離を維持する。コスト削減、軽量化、並列化を理由に、監査SAへ実装経緯・事前評価を渡したり、レビューSAへ監査結果本文・監査SAの指摘内容・判断理由・個別評価を渡したりしてはならない。

作業規模分類は次のとおりである。親は構成判断で粗い分類として扱い、計画整理ツールは起動後に詳細見積もりとして扱う。

- Small: 明示境界が狭く、変更対象が少なく、依存関係が少ない作業。
- Medium: 複数ファイル、複数工程、または限定的な依存関係を含む作業。
- Large: 広い範囲、複数コンポーネント、段階的実行、または複数の検証観点を含む作業。
- Risky: 公開API / 認証・権限 / データ永続化 / 課金 / 秘密情報・個人情報 / テスト信頼性 / AI制御文書など、失敗時の影響が大きい作業。Risky は Small / Medium / Large と併記でき、Small でも Risky なら分離を維持する。

Risky 分類は起動判断と計画見積もりの材料であり、ケースHの閉じた起動条件を拡張しない。

トークン効率予測は次を含む。親は構成判断で概算だけを扱い、計画整理ツールは起動後に詳細判断材料として扱う。

- 入力トークン量: 各SAへ渡す契約、差分、関連仕様、ログの量。
- 出力トークン量: 草案、実装結果、監査結果、レビュー結果、再修正指示の量。
- 独立実行枠数: Plan / Implement / Audit / Review / 並列検証に相当する起動候補数。
- コンテキスト複製量: 同じ仕様、差分、ログを複数SAへ渡す量。
- 並列化オーバーヘッド: 起動メッセージ作成、結果統合、不一致整理、再起動の負荷。
- 再修正確率: 境界不明確、リスク高さ、テスト不足、依存関係不明による手戻り見込み。

分離価値評価は次を含む。

- 計画整理ツールの構造化価値: 境界、依存関係、停止条件、テスト条件を実装前に整理する価値。
- 契約照合ツールの情報制御価値: 実装経緯や自己正当化から切り離して、契約と成果物を照合する価値。
- 品質確認ツールのバイアス制御価値: 監査結果本文に影響されず、品質、設計、テスト妥当性、周辺影響を見る価値。
- 敵対的確認ツールの独立価値: 成功前提ではなく失敗仮説で、仕様の抜け・矛盾・過剰解釈を探す価値。

計画整理ツールが起動後に出力する後続証明ツール構成案は次を含めてよい。

- Implement SA省略候補: 実装・修正・ファイル変更が不要な純粋な質問、明示対象だけの非破壊レビュー、または作業単位化前の草案作成だけで終わる場合。実装・変更が必要な場合、親が直接実装してはならない。
- Audit SA軽量化候補: 明示境界が狭く、成果物と契約の照合観点を絞れる場合。軽量化は監査観点と関連仕様の最小化に限り、Audit Contract と必要な関連仕様だけを渡す情報遮断は維持する。
- Review SA省略候補: PRレビュー相当の品質確認対象となる差分が存在しない場合、または正本で省略可が明示された場合。実装SAの成果物を監査SAへ渡し、監査SAの停止指摘0件後に進む場合、レビューSAは必ず起動する。
- 並列独立実行枠候補: 変更を伴う並列は §パラレル起動の独立性基準を満たす場合だけ候補にし、非破壊検証の並列はケースG / H の条件に従う。並列化はコンテキスト複製量と結果統合コストを明示する。

計画整理ツールは、Detailed Planning / Detailed Estimate を出す場合、次を明示する。

- 作業規模分類と根拠。
- Risky 該当有無と根拠。
- 親が選択した最小証明セットの整理。
- 並列稼働、情報制御、バイアス制御の評価結果。
- Orchestration Cost Gate の評価結果。
- 必要最小限の後続証明ツール構成案。
- 省略、軽量化、並列化の候補と不可理由。
- 情報分離維持条件。
- 不足している境界項目または親判断が必要な項目。

構成判断と Detailed Planning / Detailed Estimate は、次を禁止事項として扱う。

- コスト削減を理由に Audit / Review の情報分離を壊す。
- コスト削減を理由に必要なバイアス制御を省く。
- Small 判定だけを理由に監査、レビュー、情報分離を外す。
- Small でも Risky なのに必要な分離を軽量化で省く。
- 親の直接実装を許す。
- Review 省略条件をレビュー必須ルールより広く扱う。
- 並列化を理由に対象、範囲、完了条件、品質基準、実行許可を曖昧にする。

## Dependency Planning
Dependency Planning は、作業を有向グラフとして扱う計画観点である。各タスクは前提条件、完了条件、依存先、計画上の並列可能性を保持する。

依存関係があるタスクは無理に並列化しない。依存関係がないタスクは、待ち時間、確認回数、手戻りを減らすために計画上の並列可能性として扱う。Dependency Planning は、不要な確認、無駄な待ち時間、実装後の手戻りを最小化するために使う。物理並列の実行許可は §パラレル起動の独立性基準 に従う。

## Parallel Scheduling
Parallel Scheduling は、独立したタスクを物理的に同時実行する標準動作ではない。依存関係上独立して扱える作業を計画上の並列可能性として識別することを指す。

依存関係がない作業は、速度向上のために、同時実行ではなく実行順序候補と分割候補の観点で扱う。Parallel Scheduling は、対象・範囲・完了条件・品質基準・実行許可を満たす範囲で計画観点として扱う。並列可能性の整理によって境界が不明確になる場合、AI は並列可能扱いせず、必要な境界を返す。変更を伴う並列の実行許可は §パラレル起動の独立性基準 に従う。

## Plan→Execution の受け渡し契約
Plan 成果物を実装SAの入力に含める場合、親エージェントは Execution Contract として渡す。Execution Contract は実行許可を生成しない。実行は、承認済み実装指示書または作業単位化条件に基づき、§作業単位化判定フローで `target / scope / done / tests / stop` に整理できる場合だけ行う。

Execution Contract は、Plan 成果物を Execution がそのまま実行入力として消費するために、最低限以下を含む。

- Goal: 達成すべき結果。
- Scope: 対象と範囲。
- Constraints: 禁止、停止、除外操作、制約。
- Completion Criteria: 完了条件と品質基準。
- Task Graph: 作業要素、前提条件、依存先、独立性。
- 実行順序: Task Graph に基づく実行順序。
- 並列可能性: 物理並列ではなく、依存関係上独立して扱える計画上の独立性。
- 停止条件: Execution が作業を止めて返す条件。
- Replan条件: Plan へ戻す観測事実。
- テスト要求: 展開済みテスト条件または `なし（根拠）`。

証明道具箱方式において、Execution Contract は実行側に渡す最終権威である。構成判断ログや後続証明ツール構成案は、Execution Contract を生成または拡張する権威ではない。Execution Contract は、上記の意味を保ったうえで、最低限次の機械可読項目を含む。

- `target_files`: 変更または確認対象ファイル。
- `scope`: 対象範囲。
- `done_condition`: 完了条件。
- `forbidden_operations`: 禁止操作、除外操作。
- `execution_instructions`: 実行側への指示。
- `selected_tools`: 選択された証明ツール。
- `execution_frames`: 証明ツールを載せる独立実行枠。
- `required_evidence`: 必要な証拠。
- `required_checks`: 必要な確認。
- `verification_commands`: 展開済みテストコマンドまたは `なし（根拠）`。
- `block_conditions`: 停止条件。
- `output_contract`: 出力契約。

Goal Definition / Dependency Planning / Task Graph / Parallel Scheduling / Replan条件 / Quality Gate は、Plan 成果物を整理するための計画観点である。これらは実装、監査、レビュー、停止、完了判定の手順を変更しない。

Execution Contract の Goal / Scope / Constraints / Completion Criteria は、対象・範囲・完了条件・品質基準・実行許可と矛盾してはならない。Quality Gate は、Execution Contract が境界項目と矛盾しないことを確認対象に含める。

Execution が判断してよい範囲は、Execution Contract と `target / scope / done / tests / stop` の範囲内で完結する以下に限る。

- 実装方法の詳細
- ファイル編集順
- 許可範囲内で実装に直接必要な軽微なリファクタリング
- ツール選択

Execution は、以下を観測した場合、自力で Contract を更新せず、Plan へ戻すべき観測事実として停止理由に含める（§Replan の受け渡し契約）。

- Scope変更が必要である。
- Goal変更が必要である。
- Contract違反がある。
- 大きな設計変更が必要である。
- 新しい依存関係を発見した。

## Replan の受け渡し契約
Replan の受け渡し契約は、Execution / Audit / Review が実行中または照合中に得た観測事実を Plan へ戻すための契約である。ライフサイクル上の位置づけは §Execution Lifecycle の Replan 段階に従う。

Execution は、Scope変更・Goal変更・Contract違反・大きな設計変更・新しい依存関係の発見を観測した場合、自力で Contract を更新せず、Plan へ戻すべき観測事実として停止理由に含める。Scope変更が必要か、Goal変更が必要かは、Execution が観測事実として返すだけである。Execution / Audit / Review は再計画の判断を下さない。作業単位化し直すか、Plan へ戻すかの判断は親エージェントが保持する。

Replan条件に該当する観測事実は、監査SAが再計画するための入力ではない。監査SAは、その観測事実が Execution Contract、`target / scope / done / tests / stop`、差分、テスト結果、停止理由と矛盾していないかだけを照合する。監査SAとレビューSAは自己再計画しない。この情報遮断は Orchestration Cost Gate より優先される。

停止指摘または重大指摘が承認済み範囲内で最小修正可能なら、親エージェントは作業単位化し直して実装SAへ渡す。自動修正の回数制御は §自動修正ループ に従い、Replan の受け渡し契約は回数制御の再定義、拡張、条件追加を含めない。

Replan へ戻す観測事実は、Goal 達成までの計画更新に必要な入力である。新しい情報、エラー、テスト結果、監査結果、レビュー結果、依存関係の変化を含む。

## Execution→Audit の受け渡し契約
実装SAの成果物を監査SAへ渡す場合、親エージェントは Audit Contract として渡す。Audit Contract は実行許可を生成せず、監査SAが計画や実装を再設計・改善するための入力ではない。監査SAは、Audit Contract と成果物が一致しているかだけを非破壊で照合する。

Audit Contract は、Execution の成果物を Audit が契約照合対象として消費するために、最低限以下を含む。

- 実装指示書。
- Execution Contract。
- `target / scope / done / tests / stop`。
- 変更ファイル。
- 差分。
- テスト結果。
- 停止理由。
- Replan条件に該当する観測事実。
- 監査観点。

必要な関連仕様は、Audit Contract と成果物の一致確認に必要な範囲だけ補助入力として渡す。実装経緯、背景、事前評価、親の事前判断は渡さない。この情報遮断は Orchestration Cost Gate、監査軽量化、並列化より優先される。

監査観点は照合範囲を絞るための項目であり、監査SAの責務を再設計、実装改善、品質改善レビュー、計画更新へ広げない。

Replan条件に該当する観測事実は、監査SAが再計画するための入力ではない。監査SAは、その観測事実が Execution Contract、`target / scope / done / tests / stop`、差分、テスト結果、停止理由と矛盾していないかだけを照合する。

## レビューSA入力
レビューSAは、監査SAの停止指摘0件を起動ゲートとして、非破壊の PRレビュー相当品質確認だけを行う。親エージェントはレビューSA入力を以下に限定する。

- `review.md` の本文または要約。
- 承認済み実装指示書。
- 差分。
- テスト結果。
- 必要な関連仕様。AI制御文書が変更対象の場合、変更後の当該文書全体は必要な関連仕様として扱う。
- レビュー観点。
- 監査SAの停止指摘0件という起動ゲート事実。

監査結果本文、監査SAの指摘内容、判断理由、個別評価はレビューSA入力に含めない。親エージェントは完了判定、関所管理、自動修正可否判断のために監査結果を保持するが、それはレビューSAへ渡す入力ではない。この情報遮断は Orchestration Cost Gate、レビュー省略候補、並列化より優先される。

## SA利用ケース
親エージェントが SAを起動するのは以下に限定する。

| # | ケース | 目的 |
|---|---|---|
| A | プロンプト・コマンドの実行確認 | 副作用を隔離し、親のコンテキストを汚染しない |
| B | 独立した作業単位のパラレル実行 | 独立性基準を満たす作業単位を同時進行する |
| C | 事前知識なし監査 | 文脈汚染のない視点で差分・仕様を照合する |
| D | 製造→監査→レビュー→修正 自動ループ | 停止指摘 / 重大指摘0件になるまで反復改善する |
| E | 指示書草案作成 | 指示書作成の明示依頼時、または実装・変更の意図がありながら境界未確定のとき草案を作る |
| F | PRレビュー相当の品質確認 | 監査SA通過後に品質・設計・テスト妥当性を非破壊で確認する |
| G | 関心を直交分解した監査の並列起動 | 監査を関心ごとに狭くスコープし、自己正当化の余地を消す |
| H | 同一成果物の多視点並列検証 | 予断ゼロの複数視点で同一差分を並列検証し、合意 / 不一致を露出する |

ケースEは、次のいずれかで起動する。(1) ユーザーが指示書作成を明示依頼した。(2) ユーザー入力が実装・変更の意図を含み、作業単位化に必要な対象・範囲・完了条件・品質基準・実行許可を推定なしで確定できない。非破壊レビュー依頼、純粋な質問、既に承認済み実装指示書がある場合、対象・範囲・完了条件・品質基準・実行許可を推定なしで確定でき直接作業単位化できる場合は起動しない。

ケースEの起動は草案作成までであり、実行境界を生成しない。親は §Parent→Plan の受け渡し契約に従ってプランSAへ入力を渡す。草案は実行許可ではなく、プランSA自身も補完禁止に従い、対象・範囲・完了条件・品質基準・実行許可を推定なしで確定できない場合は不足項目を返す。親は草案から実装SAへ自動で進まず、実行は明示許可または作業単位化条件に従う。条件付き事前承認の除外操作（`commit` / `push` / `deploy` / 外部送信）は §条件付き事前承認テンプレート に従い、草案では実行許可扱いにしない。

SA起動判断では、作業規模だけで起動または省略を決めない。親は §構成判断 / Orchestration Cost Gate 要件の構成判断を使う場合でも、この表のSA利用ケース、作業単位化判定フロー、監査SAとレビューSAの情報分離、レビューSA必須ゲートを維持する。Orchestration Cost Gate の結果は、並列稼働・情報制御・バイアス制御で必要とされた分離を弱める根拠にしない。

ケースGは、監査SAを一本のロールプロンプトのまま、親が関心（仕様一致 / 捏造検出 / テスト改竄検出 / 完了偽装検出など）ごとにスコープを絞って並列起動する。ロールプロンプトを関心ごとに分割しない。

ケースHは、作業単位が次のいずれかに該当する場合に限り起動する。該当しない作業単位は単一監査と単一レビューとする。親は高リスクを推定で判定しない。

- 指示書またはユーザー入力が多視点並列検証を明示している。
- 変更が閉じた列挙（公開API / 認証・権限 / データ永続化 / 課金 / 秘密情報・個人情報）に触れる。

## パラレル起動の独立性基準
独立性基準は、変更を伴う並列（ケースB）に適用する。変更を伴う並列は以下をすべて満たす場合のみ可とする。

1. 変更対象ファイルに重複がない。
2. 実行順序の依存関係がない。
3. 共有リソースへのアクセスが重複しない。

途中で独立性が崩れた場合は後発SAを停止し、先発SA完了後に直列で再起動する。

非破壊検証の並列（ケースG / H）は何も書き込まないため、同一成果物に重複してよく、独立性基準を適用しない。親は各検証SAへ渡すスコープと観点だけを変え、起動時の予断（実装経緯・事前評価・他SAの指摘内容・判断理由）を渡さない。多視点並列検証の結果は、合意と不一致を分けてユーザーへ示し、不一致を握りつぶさない。

## サブエージェント起動
親エージェントは、SA起動時に、そのSAに対応するロールプロンプトを明示的に渡す。

```text
プランSA: prompts/plan.md
実装SA: prompts/implement.md
監査SA: prompts/audit.md
レビューSA: prompts/review.md
```

SAがリポジトリ上の `AGENTS.md` を自動読込する前提にしない。

SA起動時は、必要な情報を起動メッセージに含める。

- ロールプロンプトの本文または要約
- プランSAを起動する場合は Parent→Plan Contract（ユーザー要求 / 明示された対象 / 明示された範囲 / 制約 / 実行許可の有無 / 既定テスト定義 / 条件付き事前承認 / SSOT / 構成判断ログ）
- 独立実行枠を起動する場合は、その枠へ載せる証明ツール、同一枠にまとめた理由、別枠に分離した理由
- 承認済み実装指示書または作業指示一式（条件付き事前承認テンプレートから展開した条件、既定テスト定義から展開したテスト条件を使う場合はその展開済み条件を含む）
- `target / scope / done / tests / stop`
- Plan 成果物を実装SAへ渡す場合は Execution Contract（Goal / Scope / Constraints / Completion Criteria / Task Graph / 実行順序 / 並列可能性 / 停止条件 / Replan条件 / テスト要求）
- 監査SAを起動する場合は Audit Contract（実装指示書 / Execution Contract / `target / scope / done / tests / stop` / 変更ファイル / 差分 / テスト結果 / 停止理由 / Replan条件に該当する観測事実 / 監査観点）と必要な関連仕様
- レビューSAを起動する場合はレビューSA入力（承認済み実装指示書 / 差分 / テスト結果 / 必要な関連仕様 / レビュー観点 / 監査SAの停止指摘0件という起動ゲート事実）
- 禁止操作

## 各工程の確認範囲
実装SAは、明示されたテストコマンドが失敗した場合、既存ログ・テスト出力・関連ファイルを確認し、原因が承認済み範囲内に特定できた場合だけ最小修正する。原因が特定できない場合、または承認済み範囲外の場合は停止理由として返す。既定テスト定義から展開されたテスト条件は明示されたテスト条件として扱い、実装SA自身は既定テストを選ばない（§既定テスト定義）。Execution Contract が渡された場合の扱いは §Plan→Execution の受け渡し契約に従う。

監査SAは、Audit Contract と必要な関連仕様を入力として、Audit Contract 内の実装指示書、Execution Contract、`target / scope / done / tests / stop`、変更ファイル、差分、テスト結果、停止理由、Replan条件に該当する観測事実、監査観点を照合する。

監査SAは、Audit Contract 内の実装指示書に含まれる条件付き事前承認テンプレートから展開された条件、既定テスト定義から展開されたテスト条件、テスト期待値変更、テスト条件未充足、完了条件の達成扱いが差分・テスト結果・関連仕様で支えられない完了偽装を照合し、契約違反を停止指摘にする。

監査SAは、テスト自体の改竄（reward hacking）を完了偽装と並ぶ一次照合に含める。`# noqa`・skip・xfail の追加、失敗パスの mock / stub での握りつぶし、assertion の緩和は、テスト結果を成果物として信頼できなくするため停止指摘とする。

レビューSAは、レビューSA入力だけを入力として、契約準拠の判定工程を変更せず、コード品質、設計、テスト妥当性、保守性、実行時リスクを確認する。

レビューSAは、テストの実質性と周辺影響を確認する。assertion不在、常時pass、主要分岐未検証、過剰mock、失敗パスの握りつぶしはテスト妥当性リスクとして扱う。差分だけで影響判断できない場合は、変更関数・API・設定キーなどの呼び出し元 / 参照元を必要最小限で確認する。

## Continuous Verification
Continuous Verification は、品質確認を終端処理ではなくライフサイクル全体に組み込む仕組みである。速度を下げるためではなく、後戻りを減らして最終的な完了時間を短くするために使う。

Verification は次の段階で行う。

- Planning: 計画が Goal、対象・範囲・完了条件・品質基準・実行許可、制約と矛盾していないことを確認する（§Parent→Plan の受け渡し契約・§Plan→Execution の受け渡し契約の Quality Gate観点）。
- Execution: 作業が対象と範囲から逸脱していないことを確認する（§各工程の確認範囲）。
- Verification: 成果物、差分、テスト結果、仕様照合を確認する（§Execution→Audit の受け渡し契約・§レビューSA入力・§各工程の確認範囲）。
- Replan: 計画更新後も品質基準と制約を満たしていることを確認する（§Replan の受け渡し契約）。

Continuous Verification は、監査SAとレビューSAの情報分離、指摘分類、レビュー必須ゲートを弱めない。契約準拠の判定は監査SA、PRレビュー相当の品質確認はレビューSAが担い、親エージェントが関所として証拠を保持する。

## 指摘分類
監査SAは、停止指摘 / 任意指摘 / 範囲外指摘を使う。

- 停止指摘: 完了条件または品質基準を満たさないため、修正が必須。
- 任意指摘: 今回の完了を妨げない改善。修正は任意。
- 範囲外指摘: 今回の実装指示書の範囲外であり、今回の作業単位では扱わない。

レビューSAは、重大指摘 / 改善指摘 / 補足 / 範囲外指摘を使う。

- 重大指摘: 承認済み範囲内で、マージ前に直すべき明確な欠陥または高リスク。
- 改善指摘: 今回の完了条件を妨げない品質改善。
- 補足: 修正要求ではない判断メモ。
- 範囲外指摘: 承認済み範囲外、仕様拡張、別機能、任意リファクタ、設計変更要求。

監査SAの指摘分類とレビューSAの指摘分類は混ぜない。監査SAの分類は親エージェントの関所管理に保持し、レビューSA入力やレビューSAの分類へ移さない。

レビューSAの改善指摘 / 補足 / 範囲外指摘は自動修正対象にしない。

## 親エージェント
親エージェントは、承認済み実装指示書または承認済み実装指示書と矛盾しない作業単位化対象の最新ユーザー入力を読み、委任可否を判断し、SAを起動し、結果を管理する。

親エージェントの希少資源は人員でなく、コンテキストと信頼である。中核責務は二つに収束する。

- コンテキスト経路設計: どの SA に何を見せ何を見せないかを起動時に決める。特に監査SAへ渡す情報は Audit Contract と必要な関連仕様に限定し、実装経緯・事前評価を渡さない。レビューSAへ渡す情報はレビューSA入力に限定し、実装経緯・事前評価・監査結果本文・監査SAの指摘内容・判断理由・個別評価を渡さない。
- 関所強制: 親は証拠（差分・テスト結果・監査結果）を保持し、揃うまで次段へ通さない。停止指摘 / 重大指摘が残る間はマージへ進めない。

自動修正ループのループ制御・回数カウント・上限判定は親エージェントが管理する（§自動修正ループ）。

親エージェントは以下を行う。

- ユーザー指示を受ける。
- 依頼をまず委任可能か判断する。
- 独立実行枠の起動前に構成判断として、希望成果物、最小証明セット、Risk / Ambiguity / Impact / Proof Gap、証明ツールを追加する価値、独立実行枠へ分離する価値、並列稼働・情報制御・バイアス制御の必要性だけを粗く分類する。
- 構成判断では、実装計画の詳細化、Task Graph の具体化、Done補完、Scope補完、テスト条件推定、実装判断をしない。
- 構成判断では、必要な証明ツール、同じ独立実行枠にまとめる証明ツール、別の独立実行枠へ分離する証明ツール、採用しない証明ツールが過剰コストとして説明できるかだけを判定対象にする。
- 構成判断ログを残す。
- 明示された文書・差分の非破壊レビュー依頼を、明示対象に限り直接扱う。
- 条件付き事前承認テンプレートを使う場合は、テンプレートIDと全項目の条件充足を推定なしで照合する（§条件付き事前承認テンプレート）。
- 既定テスト定義を使う場合は、既定テストIDと適用条件を推定なしで照合し、テスト条件を展開する（§既定テスト定義）。
- `target / scope / done / tests / stop` に分解できる場合は、実装SA向けに整理して起動する。
- 実装結果、テスト結果、監査結果、レビュー結果を受け取る。
- 停止指摘 / 任意指摘 / 範囲外指摘を確認する。
- 監査SAの停止指摘0件後、必ずレビューSAを起動する。
- レビューSA起動時は、監査結果本文ではなく、監査SAの停止指摘0件という起動ゲート事実だけを渡す。
- レビューSAの重大指摘 / 改善指摘 / 補足 / 範囲外指摘を確認する。
- 停止指摘または重大指摘が承認済み範囲内で最小修正可能なら、作業単位化し直して実装SAへ渡す（自動修正の可否条件は §自動修正ループ）。
- 任意指摘、改善指摘、補足、範囲外指摘を自動修正対象から外す。
- 原因不明または指示書不足を推定で埋めて継続しない。
- 範囲外、仕様変更、テスト期待値変更、原因不明の場合は停止する（§停止条件）。
- 条件付き事前承認の条件充足を推定で判断する必要がある場合は停止する。
- 条件付き事前承認テンプレートまたは既定テスト定義を一意に照合できない場合は停止する。
- 最終結果をユーザーへ返す。

## 自動修正ループ
製造、監査、レビューを行い、停止指摘または重大指摘が残る場合だけ、修正、再監査、再レビューを反復する。

初回実装は回数に含めず、自動再修正試行だけを最大5回まで数える。監査SAの停止指摘0件かつレビューSAの重大指摘0件になった時点で終了し、5回目の自動再修正後も停止指摘または重大指摘が残る場合は停止する。6回目の自動再修正は開始しない。

同一の停止指摘が連続2回再発した場合、または同一の重大指摘が連続2回再発した場合も停止する。

5回上限・同一指摘再発・停止条件で自動修正ループを止める場合、親エージェントはボトルネック、反復している指摘、次に人間が判断すべき点を3行以内でユーザーへ返す。

自動修正してよい条件は以下すべてを満たす場合だけである。

- 指摘が監査SAの停止指摘またはレビューSAの重大指摘である。
- 原因が承認済み実装指示書の対象内である。
- 修正対象が承認済み変更範囲内である。
- 修正が完了条件を変更しない。
- 修正が仕様を変更しない。
- 修正がテスト期待値を変更しない。
- 修正が便乗改善を含まない。
- 最小変更で対応できる。

## 停止条件
親エージェントは、§自動修正ループ の可否条件を満たさない場合、および §作業単位化判定フロー の停止手順に該当する場合に停止する。ループ機構（回数上限・同一指摘の連続2回再発・5回目後の残存）の判定は §自動修正ループ に従う。

ループ機構以外で、親エージェントが自動修正ループを停止する場合は以下とする。

- 指摘が任意指摘である。
- 指摘が範囲外指摘である。
- レビューSAの指摘が改善指摘または補足である。
- 指摘対応に仕様変更が必要である。
- 指摘対応に変更範囲の拡張が必要である。
- 指摘対応に対象外ファイル変更が必要である。
- 指摘内容と実装指示書が矛盾している。
- 最小修正では対応できない。
- 原因を推定で決める必要がある。
- テスト期待値変更が必要である。
- 必要なロールプロンプトを渡せない。
- 承認済み実装指示書がない。
- 対象・範囲・完了条件が未定義である。
- テスト条件が未定義で、テスト実行が必要である。
- 条件付き事前承認の条件充足を推定で判断する必要がある。
- 条件付き事前承認テンプレートまたは既定テスト定義を一意に照合できない。

## Toolbox / 証明道具箱
Toolbox は、Planning Engine が選択できる手段の集合であり、証明道具箱方式では希望成果物の安全証明に使う証明ツールの一覧として扱う。実行主体ではない。Planning Engine が、対象・範囲・完了条件・品質基準・実行許可、制約、Quality Gate、依存関係、最終的な完了時間を踏まえて、最適な証明ツール、最適な独立実行枠、最適な実行方法を選択する。

Toolbox は次の種類を持つ。

- 読取: 対象ファイル、差分、仕様、ログ、テスト出力の確認
- 編集: 承認済み範囲への変更
- 検証: 明示されたテスト、静的確認、差分照合、仕様照合
- 監査: Audit Contract と成果物の非破壊照合
- レビュー: 品質、周辺影響、テスト妥当性の非破壊確認
- 報告: 実施内容、変更ファイル、確認結果、停止理由の返却

Toolbox の利用は、権限ではなく条件付き能力である。道具が利用可能でも、承認済み範囲・実行許可が許さない操作は行わない。親の直接実装禁止、情報分離、バイアス制御、除外操作（`commit` / `push` / `deploy` / 外部送信）は Toolbox の利用可否より優先される。証明ツールの選択は実行許可を生成せず、独立実行枠への分離は実行契約の境界を拡張しない。

## Quality Gate
Quality Gate は、Planning / Execution / Verification / Replan の各段階で継続的に品質を確認する仕組みである。終端処理だけではない。計画が正しくても実行が逸脱する場合があり、実行が正しくても新しい情報によって計画更新が必要になる場合がある。

Quality Gate は次を確認する。

- Goal と対象・範囲・完了条件・品質基準・実行許可から逸脱していない。
- 制約に抵触していない。
- 明示されたテスト条件が扱われている。
- テスト期待値、停止条件、禁止操作が変更されていない。
- SSOT と矛盾していない。
- 成果物と確認結果で完了扱いを支えられる。
- 監査SAとレビューSAの情報分離が維持されている。
- 監査SAの停止指摘0件後にレビューSAが起動されている。

Quality Gate を満たせない場合、作業は Goal Complete として扱わない。

## Goal Complete
Goal Complete は、要求を満たし、品質基準を満たした状態である。単に実装が終わった状態ではない。成果物、確認結果、テスト結果、制約照合によって、要求が満たされたことを説明できる状態である。

Goal Complete は §完了条件 の成立を前提とする。実装SAの実装とテスト結果、監査SAの監査結果、レビューSAのレビュー結果が揃い、停止指摘0件かつ重大指摘0件の場合のみ成立する。Goal Complete に到達できない場合、AI は未達の条件、停止理由、次に必要な判断を返す。

## Contract
Contract は、Planning Engine が最適化を行う際の制約条件である。計画を固定するものではない。Contract はゴール、制約、完了条件を保持し、Planning Engine はその範囲内でタスク構成、実行順序、計画上の並列可能性を決定する。

Contract は次を保持する。

- `goal`: 達成すべき結果
- `scope`: 対象と範囲
- `constraints`: 禁止、停止、除外操作
- `done`: 完了条件
- `quality_criteria`: 品質基準

Contract に未定義の境界を AI が補完してはならない。Contract が不足している場合、AI は不足項目を返す。個別の受け渡し契約（Parent→Plan / Plan→Execution / Execution→Audit / Audit→Review / Replan）の構成項目と情報分離は、各契約節を正本とする。

## Constraints
Constraints は、Planning Engine と Execution が越えてはならない境界である。個別の禁止・停止規則は各節（§停止条件・§自動修正ループ・§各工程の確認範囲・各受け渡し契約）を正本とし、本節はまとめである。

Constraints は次を含む。

- AI は対象、範囲、完了条件、品質基準、実行許可を補完しない。
- SSOT の採用・変更は人間が保持する判断である。AI が推定で採用・変更しない。
- `commit` / `push` / `deploy` / 外部送信は、別途明示許可がある場合だけ行う。
- テスト期待値の変更、skip、xfail、assertion 緩和、失敗パスの握りつぶしを完了の近道にしない。監査SAはこれをテスト改竄（reward hacking）として完了偽装と並ぶ一次照合で停止指摘にする。
- 便乗リファクタ、命名変更、移動、削除、構成変更を承認済み範囲外で行わない。
- 原因不明の探索的修正を行わない。
- 情報遮断とバイアス制御は Orchestration Cost Gate より優先される。Audit / Review の情報分離、敵対的確認の独立性、契約照合と品質判断の分離がコスト削減、並列化、軽量化より優先される。
- 親エージェントは実装・修正・テスト・監査・PRレビュー相当の品質確認・指示書作成を直接行わない。構成判断 / 軽量化を抜け道にしない。
- 草案・Plan成果物・条件付き事前承認テンプレートID・既定テストID は実行許可を生成しない。

Constraints に抵触する場合、AI は作業を停止し、抵触した境界を返す。

## PR作成
親エージェントが PR を作成する場合は、以下に従う。

- PR のタイトル・本文・見出しは、対象リポジトリの言語規約に従う。
- 言語規約が未指定の場合は、ユーザーとの会話で使われている主要言語に合わせる。
- コマンド名、ログ、API名、ファイル名、ブランチ名、エラー本文などは原文のままでよい。
- PR テンプレートがある場合は、その構成に従う。

## 親の最終出力様式
親エージェントは、最終結果を以下の様式でユーザーへ返す。

- 結論先出しで返す。
- 実装・テスト・監査・レビュー結果、停止指摘 / 重大指摘の有無、自動再修正回数、停止理由を返す。
- 自動修正ループを打ち切る場合は §自動修正ループ の様式（ボトルネック / 反復指摘 / 次に人間が判断すべき点・3行以内）で返す。

## AIへ委譲する判断
AIへ委譲する判断は、Contract の範囲内で完結する仮決定に限る。

AI は次を判断してよい。

- Goal 達成に必要なタスク分解
- タスク間の依存関係
- 計画上並列可能な作業
- 実行順序と優先順位
- Toolbox から使う道具
- 実行中の計画更新
- 明示されたテスト条件に基づく実行と結果整理
- 差分、テスト結果、仕様の照合
- Constraints に抵触した場合の停止
- 不足している Contract 項目の列挙

AI は、委譲された判断を Contract の拡張に変換してはならない。Execution 単体へ委譲する判断は、実装方法の詳細、ファイル編集順、Contract 範囲内で実装に直接必要な軽微なリファクタリング、Toolbox 選択に限る。Goal変更、Scope変更、Contract違反、大きな設計変更、新しい依存関係の発見は、Replan へ戻す観測事実として扱う。

## 人間が保持する判断
人間が保持する判断は、作業境界とリスク受容に関わる決定である。

人間は次を保持する。

- 目的、対象、範囲、完了条件、品質基準、実行許可の確定
- SSOT の採用、変更、優先順位の決定
- Contract 外の仕様変更、構成変更、対象拡張の判断
- `commit` / `push` / `deploy` / 外部送信の許可
- テスト条件が不足している場合の追加定義
- 停止後に作業を続けるかどうかの判断
- 作業単位化し直すか、Plan へ戻すかの判断

AI は、人間が保持する判断を推定で代替しない。

## SSOT
SSOT は、判断の根拠として優先する正本である。

- 現行運用ルールの SSOT は本文書 `docs/orchestration-process.md` である。
- 設計理由と書き味の SSOT は `docs/prompt-guide.md` である。
- 本文書へ採用された運用構造の設計履歴/rationale は `docs/orchestration-v2.md` である。現行運用ルールではない。

矛盾がある場合、現行運用では本文書を優先する。SSOT の採用、変更、優先順位の決定は人間が保持する判断である。

## Success Criteria
このプロセスの成功条件は、単に実装が完了したことではない。最小時間で要求を満たし、品質基準を満たした状態に到達することである。

成功には次を含む。

- Goal が達成されている。
- 対象・範囲・完了条件・品質基準・実行許可、制約から逸脱していない。
- Quality Gate を満たしている。
- 監査SAとレビューSAの情報分離、レビュー必須ゲート、停止条件、完了判定が維持されている。
- 依存待ち、不要確認、手戻り、コンテキスト切替が最小化されている。
- 成果物と確認結果によって完了を説明できる。
- 判断ログにより、証明ツールの選択・非選択、同一枠化、分離理由を説明できる。

品質と速度を両立することが、このオーケストレーションの責務である。品質維持、情報分離、バイアス制御は速度に優先する。軽量化は安全性削減ではなく証明コスト削減として扱う。

## 完了条件
このプロセス仕様は、本文ルールの再掲による自己検査であり、新規ルールを足さない。以下を各節の成立条件への参照として満たすとき有効である。

- 指示書作成が実装指示書を作り、親エージェントが承認済み実装指示書を管理し、親エージェントが直接実装しない（§基本方針・§親エージェント）。
- 親エージェントが §SA利用ケース 以外で SAを起動しない。
- 実装SAが `prompts/implement.md`、監査SAが `prompts/audit.md`、レビューSAが `prompts/review.md` に従う（§サブエージェント起動）。
- 監査SAへ渡す情報が Audit Contract と必要な関連仕様に限定され、レビューSAへ渡す情報がレビューSA入力に限定される（§Execution→Audit の受け渡し契約・§レビューSA入力・§親エージェント）。
- 実装SAの成果物を監査SAへ渡す場合、Audit Contract が実装指示書、Execution Contract、`target / scope / done / tests / stop`、変更ファイル、差分、テスト結果、停止理由、Replan条件に該当する観測事実、監査観点を含み、監査SAが契約と成果物の一致確認だけを行う（§Execution→Audit の受け渡し契約）。
- 監査SAがテスト改竄（reward hacking）を完了偽装と並ぶ一次照合に含める（§各工程の確認範囲）。
- 多視点並列検証（ケースH）が閉じた起動条件に該当する場合だけ起動される（§SA利用ケース）。
- レビューSAが監査SAの停止指摘0件後に、監査結果本文、監査SAの指摘内容、判断理由、個別評価を受け取らず、PRレビュー相当の品質確認を非破壊で行う（§レビューSA入力・§親エージェント・§各工程の確認範囲）。
- SAが `AGENTS.md` 実ファイルを自動読込する前提にせず、ロールプロンプトと禁止操作が起動メッセージで明示される（§サブエージェント起動）。
- 監査SAの停止指摘とレビューSAの重大指摘のみが範囲内自動修正対象になり、自動ループのループ制御・回数カウント・上限判定は親エージェントが管理する（§自動修正ループ・§親エージェント）。
- 条件付き事前承認が、明示条件を満たすことを推定なしで確認できる場合だけ作業単位化条件として扱われ、条件付き事前承認テンプレートと既定テスト定義は、IDと展開条件を推定なしで照合できる場合だけ使われる（§条件付き事前承認テンプレート・§既定テスト定義）。
- 親エージェントの初動が構成判断から始まり、固定SA起点ではなく、最小証明セット、証明ツールの追加条件、独立実行枠への分離条件、判断ログを扱う（§証明道具箱方式・§構成判断 / Orchestration Cost Gate 要件・§親エージェント）。
- プランSAを起動する場合、Parent→Plan Contract が明示入力と正本参照だけを渡し、Plan 段階の計画観点と禁止事項を分離している（§Parent→Plan の受け渡し契約）。
- 構成判断 / Orchestration Cost Gate を扱う場合、親の構成判断と計画整理ツールの Detailed Planning / Detailed Estimate が分離され、親が独立実行枠起動前の粗い構成判断と判断ログだけを行い、計画整理ツールが起動後の詳細計画見積もりだけを行う（§構成判断 / Orchestration Cost Gate 要件・§親エージェント）。
- 最小証明セットから始め、並列稼働・情報制御・バイアス制御が Orchestration Cost Gate より先に評価され、Audit / Review の情報分離と敵対的確認の独立性がコスト削減より優先される（§構成判断 / Orchestration Cost Gate 要件）。
- Plan 成果物を実装SAへ渡す場合、Execution Contract と `target / scope / done / tests / stop` が同じ境界を示し、Execution が判断してよい範囲と Plan へ戻す条件が分離されている（§Plan→Execution の受け渡し契約・§Replan の受け渡し契約）。
- コード変更を含む作業単位ではテストコマンド必須である（§既定テスト定義）。
- 停止条件に該当した場合は停止する（§停止条件・§自動修正ループ）。
- 完了判定は、実装SAの実装とテスト結果、監査SAの監査結果、レビューSAのレビュー結果が揃い、停止指摘0件かつ重大指摘0件の場合のみ成立し、Goal Complete をスキップしない（§Goal Complete・§Quality Gate）。
- 計画最適化の優先順位が Goal 達成、品質維持、実装時間短縮、手戻り最小化、コンテキスト切替最小化の順であり、品質維持と情報分離が実装時間短縮に優先する（§Optimization Principle）。
- プロセスの成功が、最小時間で要求を満たし、品質基準を満たした状態への到達であり、情報分離、レビュー必須ゲート、停止条件、完了判定の維持を含む（§Success Criteria）。

## 制約
このプロセスは、プロンプト駆動の責務分離である。

以下は保証しない。

- SAが起動時に `AGENTS.md` 実ファイルを自動読込すること（§サブエージェント起動）。
- SAがロールプロンプト実ファイルを自動読込すること。
- 親エージェントが直接実装できないことのツールレベル強制。
- 実行権限のハード分離。
- SA起動仕様そのものの変更。
