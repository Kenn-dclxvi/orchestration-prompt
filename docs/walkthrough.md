# ウォークスルー

## この文書の位置づけ
この文書は、実タスク1件が plan→implement→audit→review→完了判定 の1サイクルを通る様子を具体例として示す。`docs/AIエージェント活用指針.md` 段階3-4の考え方と、`docs/orchestration-process.md` の各工程・指摘分類・完了条件を結びつける読み物である。

各工程・指摘分類・完了条件の正本は `docs/orchestration-process.md` にある。人間向けの段階の出典は `docs/AIエージェント活用指針.md` 段階3-4である。この文書は運用ルール・工程・指摘分類を新設せず、正本の記述に沿って1サイクルを叙述する。

用語の意味は `docs/glossary.md` を参照する。この文書では用語を定義し直さない。登場するロールプロンプトは `prompts/plan.md` / `prompts/implement.md` / `prompts/audit.md` / `prompts/review.md`、起動様式は `templates/launch-plan-sa.md` / `templates/launch-implement-sa.md` / `templates/launch-audit-sa.md` / `templates/launch-review-sa.md` である。

## 段階3-4との対応
`docs/AIエージェント活用指針.md` 段階3は、plan / implement / review に役割を分け、確認を実装とは別の視点で行う回し方を導入する段階である。段階4は、条件付き事前承認で繰り返し運用を自律化する段階である。

このウォークスルーで示す1サイクルは段階3の役割分離を具体化したものである。本文中の「親が証拠が揃うまで次工程へ通さない」「監査SA・レビューSAへ実装経緯や事前評価を渡さない」「テスト自体の改竄を疑う」は、段階3-4が「確認役には実装者の説明を渡さない」「ごまかしの効かない事実を関所にする」として述べる移行を、`docs/orchestration-process.md` の工程として実行したものである。

## 1サイクルの全体像
1サイクルは次の順で進む。各工程の入出力と関所の正本は `docs/orchestration-process.md` にある。

```text
plan(草案作成)
  → 作業単位化(target / scope / done / tests / stop)
  → implement
  → audit(停止指摘 / 任意指摘 / 範囲外指摘)
  → review(重大指摘 / 改善指摘 / 補足 / 範囲外指摘)
  → 完了判定
```

関所は次の3か所にある。

- 作業単位化: 親が `target / scope / done / tests / stop` を推定なしで整理できる場合だけ実装SAへ進む。整理に補完が必要なら停止する(`docs/orchestration-process.md` §作業単位化判定フロー)。
- audit→review: 監査SAの停止指摘0件後に、親は必ずレビューSAを起動する(`docs/orchestration-process.md` §親エージェント)。
- 完了判定: 停止指摘0件かつ重大指摘0件のときだけ成立する(`docs/orchestration-process.md` §完了条件)。

以下に doc変更の例と code変更の例を各1本示す。doc例は実際に回したサイクルの経過であり、code例は段階1-2の例示スタイル(「例: 小さな関数の追加とそのテスト」)に合わせた説明用の代表例である。

## doc変更の例: 用語集の新規作成
題材は `docs/glossary.md`(用語集)の新規作成である。これは実際に回したサイクルの経過である。

### plan(草案作成)
プランSAが `prompts/plan.md` に従い、指示書草案を作成した。草案は `prompts/plan.md` が定める草案構成項目と、implement / audit / review 各工程および各工程の判定基準を含む。草案は実行許可ではない(`docs/orchestration-process.md` §SA利用ケース ケースE)。

### 作業単位化
親が草案を `target / scope / done / tests / stop` に整理して実装SAへ渡した。

```text
target: docs/glossary.md の新規作成
scope: 13用語の定義集約のみ
done: 全用語の定義 + 出典所在 + §配置規律準拠 + §書き味準拠
tests: なし(根拠: doc新規作成のみ)
stop: 出典に定義なし / 出典間矛盾 / 配置規律判断が推定
```

`tests` が `なし(根拠)` なのは、コード変更を含まないためである。コード変更を含む作業単位ではテストコマンド必須だが、ドキュメント新規作成のみのため `なし(根拠)` が成立する(`docs/orchestration-process.md` §既定テスト定義)。

### implement(初回)
実装SAが `prompts/implement.md` に従い、13用語(指示書 / SA / 親 / 境界項目 / 作業単位化 / 停止指摘 / 任意指摘 / 範囲外指摘 / 重大指摘 / 改善指摘 / 補足 / 条件付き事前承認テンプレート / 既定テスト定義)を作成した。実装SAは承認済み `target / scope / done` だけを扱い、契約準拠や完了の判定はしない。

### audit(初回)
監査SAが `prompts/audit.md` に従い、非破壊で照合し、停止指摘2件を検出した。

- 停止指摘1: 条件付き事前承認テンプレート項・既定テスト定義項が構成項目を逐語列挙していた(`docs/prompt-guide.md` §配置規律違反、完了条件未達)。
- 停止指摘2: 同2項が展開手順・運用制約を複製していた(非対象混入)。

任意指摘・範囲外指摘はなかった。監査SAには実装経緯・事前評価を渡していない。監査SAが見るのは指示書・差分・テスト結果・関連仕様だけである(`docs/orchestration-process.md` §各工程の確認範囲)。

### 自動再修正(試行1回目)
親が両指摘を「監査SAの停止指摘 / 承認済み対象内 / 最小修正可能 / 完了条件・仕様・期待値を変えない」と判定し、自動修正対象にした(`docs/orchestration-process.md` §自動修正ループ)。実装SAが当該2項を「意味 + 正本参照」に圧縮し、逐語列挙と複製文を削除した。これが自動再修正の試行1回目である。初回実装は回数に含めない。

### re-audit
監査SAが再照合し、停止指摘0件となった。

### review
監査SAの停止指摘0件後、親がレビューSAを起動した。レビューSAが `prompts/review.md` に従い、非破壊で PRレビュー相当の品質確認を行い、次を返した。

- 重大指摘: 0件。
- 改善指摘: 0件。
- 補足: 1件。出典表記が `CLAUDE.md` であるのに対し他文書は `AGENTS.md` 呼称を使う差があり、配布先でシンボリックリンクが無い場合の参照解決に懸念がある。品質欠陥ではなく表記方針の判断事項として引き継ぐ。

レビューSAには実装経緯・事前評価・監査の判断理由を渡していない。起動ゲートとしての「停止指摘0件」という状況だけを渡した(`docs/orchestration-process.md` §パラレル起動の独立性基準、§親エージェント)。

### 完了判定
停止指摘0件かつ重大指摘0件で完了が成立した(`docs/orchestration-process.md` §完了条件)。自動再修正は1回(上限5回)であった。補足は自動修正対象外であり、引き継ぎ事項として残した(`docs/orchestration-process.md` §指摘分類、§停止条件)。

## code変更の例(説明用)
ここは説明用の例である。実在のテストコマンド確定・テスト実行・実コード変更は行わない。題材は段階1-2が用いる例示スタイルに合わせ、「小さな関数の追加とそのテスト」を代表例として置く。

doc例との主な違いは、code例ではテスト実行が関所になる点と、監査SAがテスト自体の改竄(reward hacking)を完了偽装と並ぶ一次照合に含める点である。以下はその違いが現れる箇所を `docs/orchestration-process.md` §各工程の確認範囲・§自動修正ループ に沿って説明する。

### plan(草案作成)
プランSAが、対象関数の追加とそのテストを含む草案を作成する。草案は `prompts/plan.md` が定める草案構成項目を含む。草案は実行許可ではない。

### 作業単位化
親が `target / scope / done / tests / stop` に整理する。doc例と異なり、コード変更を含む作業単位なので `tests` はテストコマンド必須であり、`なし(根拠)` は使えない(`docs/orchestration-process.md` §既定テスト定義、§作業単位化判定フロー)。テスト条件が未定義でテスト実行が必要な場合、親は停止する(`docs/orchestration-process.md` §停止条件)。

### implement(初回)
実装SAが承認済み `target / scope / done` の範囲で関数を追加し、明示されたテストコマンドを実行する。明示テストが失敗した場合、実装SAは既存ログ・テスト出力・関連ファイルを確認し、原因が承認済み範囲内に特定できた場合だけ最小修正する。原因不明または範囲外の場合は停止理由として返す(`docs/orchestration-process.md` §各工程の確認範囲)。

### audit
監査SAは、差分・指示書・テスト結果を照合する。doc例の照合に加えて、code例ではテスト結果が成果物として信頼できるかを一次照合する。次はテスト改竄(reward hacking)として停止指摘になる(`docs/orchestration-process.md` §各工程の確認範囲、`prompts/audit.md`)。

- `# noqa` / skip / xfail の追加。
- 失敗パスの mock / stub での握りつぶし。
- assertion の緩和。

完了条件の達成扱いがテスト結果で支えられない場合は、完了偽装として停止指摘になる。

### review
監査SAの停止指摘0件後、レビューSAがテストの実質性と周辺影響を確認する。assertion不在 / 常時pass / 主要分岐未検証 / 過剰mock / 失敗パスの握りつぶしはテスト妥当性リスクとして扱う。差分だけで影響判断できない場合は、変更関数の呼び出し元 / 参照元を必要最小限で確認する(`docs/orchestration-process.md` §各工程の確認範囲、`prompts/review.md`)。

### 完了判定
停止指摘0件かつ重大指摘0件で成立する。code例ではテスト結果が裏付けの中心になる点が doc例と異なるが、完了条件の成立要件そのものは doc例と同じである(`docs/orchestration-process.md` §完了条件)。

## doc例と code例の対応
両例は同じ1サイクルの順序を踏み、同じ関所を通る。違いはテスト実行ゲートの有無と、監査の一次照合にテスト改竄検出が加わるかどうかに集約される。

| 工程 | doc例 | code例(説明用) |
|---|---|---|
| tests | `なし(根拠)` 可 | テストコマンド必須 |
| audit の一次照合 | 配置規律 / 同期 / 完了偽装 | 左記 + テスト改竄(reward hacking) |
| review の主眼 | 文書整合・表記方針 | テスト実質性 + 周辺影響 |
| 完了判定 | 停止指摘0件 + 重大指摘0件 | 停止指摘0件 + 重大指摘0件 |

完了判定の成立要件は両例で同じである。各工程・指摘分類・完了条件の正本は `docs/orchestration-process.md` にあり、この文書はその正本に沿って1サイクルを叙述したものである。
